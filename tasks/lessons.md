## 1. Масштабирование опционных премий (Scale Divisors)
* **Проблема:** В CME Daily Bulletin премии опционов по британскому фунту (GBP) указаны в центах (например, `14.23` цента для страйка 1.2000), тогда как для EURUSD они указаны в пунктах котировки с шагом 0.0001 (например, `0.01529`). Без правильной нормализации премия GBP `14.23` прибавляется напрямую к страйку `1.2000`, улетая в область `15.43` (далеко за пределы графика). Это также приводило к сбоям Brent-метода при вычислении IV (волатильность улетала до 172%, а дневная сигма — до 1400 пунктов).
* **Решение:** В советнике MT5 `CME_GEX_Levels_EA.mq5` реализована интеллектуальная нормализация:
  ```mql5

  if(g_base_currency == "GBP" && call_settle > 1.0)
      call_settle = call_settle / 100.0;
  ```

## 10. Ошибочный парсинг коротких строк без премий (Settle = Strike)
* **Проблема:** По валютным парам (особенно GBPUSD) встречались короткие строки, описывающие объемы для конкретных страйков (например, `1347 0.020 .020 *.010A ---- ----- ---- ---- ---- 2 ---- 22 2.090B .010B`), по которым не было торгов и Settle был равен `-----`. Парсер Delta ошибочно принимал котировки High/Low (например, `.020` на позиции 2) за Delta. Из-за этого вычислялся `settle_str` = `parts[delta_idx - 2]` = `parts[0]`, и сам Strike ошибочно присваивался премии Settle. После деления на 100 премия для страйка 1.347 становилась `13.47`. Затем скрипт отбирал её как Daily Settle, так как она имела ненулевой OI.
* **Решение:**
  1. Введено жесткое условие `if delta_idx < 5: continue` при поиске дельты. Поскольку первые элементы всегда заняты Strike, Open, High, Low, премия Settle и Delta физически не могут находиться левее 5-й позиции. Это немедленно отбрасывает подобные строки, избегая ложного чтения страйка как премии.
  2. Добавлена логика парсинга склеенных значений Settle и Net Change (например, `.00430-0.00130`), чтобы парсер не подставлял пустое значение в Settle при их наличии.
  После внесения правок Daily Settle по GBPUSD принял корректные значения (например, `0.0043`), что устранило "улетание" уровней от цены.

## 11. Ошибка поиска ближайшего контракта через idxmin() (Daily Month Fallback)
* **Проблема:** Если для текущего дня недели отсутствовал конкретный дневной код (например, `FRC` для пятницы), скрипт применял `fallback`-логику, агрегируя все остальные дневные коды, группируя их по месяцам и выбирая месяц с помощью `.idxmin()`. Функция `idxmin()` возвращает месяц с **наименьшим открытым интересом (OI)**, а не ближайший по дате. Из-за этого скрипт мог выбрать нерелевантный слабо-торгуемый контракт, в результате чего Settle для MDD становились мизерными (OI около 6), а уровни MDD на графике съезжали.
* **Решение:**
  1. Внедрена функция `get_nearest_month()`, которая выполняет жесткую хронологическую сортировку строк формата `MMM%y` (например, `MAY26`, `JUN26`) по году и месяцу.
  2. При срабатывании fallback скрипт теперь отбирает контракты из ближайшего по времени месяца (`nearest_month = ...[0]`), вместо поиска минимального OI.
  3. В случае отсутствия всех дневных контрактов скрипт корректно переключается на ближайшие недельные контракты (Weekly Options `1EU`-`5EU`), что для пятницы позволяет идеально подхватить текущую недельную экспирацию (например, `5EU MAY26`).
  Это обеспечило высокую релевантность дневных уровней MDD и вернуло их к текущим рыночным ценам EURUSD (Daily Call OI возрос с 6 до 2365).

## 14. Нестабильность и «плавание» форвардного сдвига (Floating Forward Offset)
* **Проблема:** Советник MT5 вычислял динамический форвардный сдвиг (`fw_offset = spot_price - futures_price`) по текущей секундной цене Close дневного бара (`iClose(Symbol(), PERIOD_D1, 0)`). Так как спотовая цена непрерывно колеблется в реальном времени, а фьючерсная цена из вчерашнего клиринга CME статична, поправка менялась на каждом тике.
